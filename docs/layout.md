# Herbier — Repository layout

Status: decided, 2026-09-16 (see Decisions at the end). Refines
`architecture.md` §9. Differences from that sketch, all deliberate: a pure
`domain/` library is added (native tests); `reference/` and `resolver/`
become `refs/` (pure decoders and projection) plus `refs_io/` (fetching);
`map/` becomes `geo/` (it also holds tiles and geocoding); `capacitor/`
becomes `bindings/` (MapLibre, pmtiles and exifr bindings live there too);
`test/`, `scripts/` and `.github/` are new. The mockup
(`design_handoff_herbier/`) stays the source of truth for screens and tokens.

## 1. Top level

```
herbier/
  dune-project            one project, three packages: `herbier` (the app), `postgrest` and `postgrest-codegen` (lib/)
  herbier.opam            generated by dune from dune-project, committed (do not edit)
  postgrest.opam          idem
  postgrest-codegen.opam  idem
  dune-workspace          the opam-repository commit `dune pkg lock` solves against
  dune.lock/              `dune pkg lock` output, committed
  .ocamlformat            version = 0.29.0, profile = default, margin = 80
  package.json            Capacitor CLI + plugins, maplibre-gl, pmtiles, exifr, esbuild, sass
  package-lock.json
  capacitor.config.ts     appId, webDir → _build/default/web/dist (filled by `dune build @web`)
  app/                    all Herbier OCaml; one dune library per subdir + main.ml (§2)
  lib/                    libraries with no Herbier-specific knowledge, publishable: postgrest/ (§2)
  web/                    shell sources: index.html, sass/, fonts/, js/, map/ (§3)
  android/                Capacitor Android project, generated then committed (§4)
  supabase/               config.toml, migrations/, schema/, scripts/, tests/ (§5)
  test/                   OCaml tests, native (§6)
  scripts/                dev loop, emulator, icon subset, PMTiles extract, release (§7)
  docs/                   stack, architecture, this file, handoff, research, notes
  .github/workflows/      ci.yml, android.yml (§7)
```

Dune units: every `app/<dir>/` is a **library** named `herbier_<dir>`;
`lib/postgrest/` is the **library** `postgrest`, in the package of the same
name, with its codegen in `lib/postgrest/codegen/`, the separate package
`postgrest-codegen` (library and native executable of that name, a
build-time tool; users of `postgrest` do not pull it, nor ppxlib); `app/main.ml` is the only app **executable** (`(modes js)`); `web/dune`
holds the copy, sass and esbuild **rules** under alias `@web`; `test/*/dune`
are **tests**. Nothing outside `app/`, `lib/`, `web/`, `test/` has a `dune`
file; `supabase/` is a data-only dir, so rules and tests can read the
catalog in `supabase/schema/`.

Dependencies are locked with `dune pkg lock` (`dune.lock/` committed), so
`dune build` alone works from a clean clone and in CI. `dune-workspace`
pins the opam-repository commit the solver reads, so adding a dependency
does not upgrade the others (or the compiler); moving that commit is a
deliberate upgrade. Dune 3.24.2 still
labels package management experimental; if a dependency will not lock or
build, the fallback is an opam switch with a lock file and nothing else
changes.

The `*.opam` files are committed so that `opam install .` and `opam pin`
find the packages. Since dune 3.23 dune no longer writes them into the
tree: it generates them under `_build/default/` and `dune build @opam` (also
`@install` and `@runtest`, hence `dune test` in CI) fails with a diff when a
committed one differs from `dune-project`. After editing `dune-project`,
refresh them with `dune build @opam --auto-promote`. Dune neither checks
nor promotes a package's opam file that is absent from the tree, so a new
package needs `touch <package>.opam` before that command.

Dependency direction (enforced by each `dune` file's `libraries` field):

```
domain    ← ptime, ptime.clock.os, uuidm, yojson
                                         (no Brr; the clock is read by Ids.fresh, UUID v7)
postgrest ← yojson, ptime, uri           (lib/; no domain, no Brr, no ppxlib)
postgrest-codegen ← ppxlib, ppx_deriving_yojson, yojson (lib/postgrest/codegen/, its own package; a build-time tool, no app library links it;
                                         postgrest only as an opam version constraint, = version: the output targets its API)
refs      ← domain, yojson               (no Brr)
bindings  ← brr
store     ← domain, bindings, postgrest, yojson, ptime, brr (for Fut)
sync      ← domain, store, bindings, postgrest, brr (for Fut)
photos | refs_io | geo   ← domain, store, bindings, brr (for Fut); refs_io also refs; photos also yojson, ptime
                                         (siblings never import each other)
ui        ← everything above + react, reactiveData
main      ← ui, brr                     (main.ml finds the root element and starts the router)
```

Notes:

- Anything testable without a browser goes in `domain/` (rules, value
  codecs), `refs/` (payload decoding and projection) or `lib/postgrest/`
  (request rendering, response decoding); these three build natively and
  under jsoo. `domain/` uses `Yojson.Safe.t` only for the `to_json` /
  `of_json` of its ids and closed value sets, which the table metadata
  names (`id=<Module>`, `ocaml=<Module>`, stack.md); rows go through `Postgrest` column types,
  never `Jv`, and external payloads are decoded in `refs/`.
- `lib/postgrest/` knows nothing of Herbier and does no HTTP; the Brr fetch
  adapter is `sync/transport.ml`. If `postgrest` is published, that adapter
  could become a `postgrest-brr` package.
- `store/` runs hand-written SQL (FTS5, group by day, place bucketing,
  joins) through the plugin and decodes its JSON rows with `Postgrest.Row`,
  which has the shape of a PostgREST row; no query DSL on the SQLite side.
  Possible upgrade, not a decision: sqlgg could type that SQL from the
  CREATE TABLE statements if its async traits can be implemented over the
  plugin (spike; see `exploratory_research/sqlgg-jsoo.md`: worth doing).
- `store/tables.ml` is generated from the catalog by
  `postgrest-codegen` and committed; `store/` and `sync/` share its
  declarations, and `dune test` fails when it is stale (a rule in
  `app/store/dune` diffs it with the generated one; `dune promote` updates
  it), so a schema change is one migration, two dumps and one promotion. Local-only tables (`outbox`, `sync_state`,
  `settings`) declare their columns next to their queries.
- Cross-service orchestration (save ⇒ outbox push ⇒ reference fetch ⇒
  geocode) lives in `ui/app.ml`, which keeps the siblings independent.
- `ui/` uses `(include_subdirs qualified)`: `Screens.Collection`,
  `Widgets.Chip`. `map_tab.ml` avoids [shadowing](shadowing) `Stdlib.Map` in `Screens`.
- The map, camera `<video>` and pinch viewer are ordinary widgets holding a
  JS object and subscribing to signals; no "islands" directory.

## 3. `web/` — static shell and build output

```
web/
  dune                    @web alias: copy index.html, fonts/, img/, map/; sass sass/app.sass →
                          dist/app.css; esbuild js/vendor.js → dist/vendor.js;
                          copy ../app/main.bc.js → dist/app.js
  index.html              loads dist/app.css, dist/vendor.js then dist/app.js
  sass/                   indented Sass syntax (.sass), not SCSS
    app.sass              entry: @use the four partials, then every screens/*.sass
    _tokens.sass          custom properties on :root; the only source of design tokens
    _base.sass            reset, @font-face, type-role, icon and photo-scrim mixins with their .t-* classes,
                          sun-readability rules (5f)
    _widgets.sass         chips, cards, tab bar, sheets, dialogs, fields, and the widget mixins
    _shell.sass           the router's shell: scrolling screen above the tab bar, screen margins
    screens/              one file per handoff screen (collection.sass, map_tab.sass, …),
                          handoff id in a header comment
  fonts/                  Manrope, Newsreader (variable woff2), Material Symbols subset
  js/
    vendor.js             esbuild entry: imports Capacitor plugins, maplibre-gl, pmtiles,
                          exifr; exposes them on globalThis.herbier for the Jv bindings
    map.js                the ~100-line MapLibre facade (architecture §8), imported by vendor.js
  map/
    positron.json         pinned OpenFreeMap style (offline.json with a pmtiles:// source: v2)
```

- Styles use the indented Sass syntax (`.sass`, not SCSS), compiled by
  dart-sass (from npm) inside the `@web` rule,
  next to esbuild: mixins and nesting keep the styles reusable and concise.
  Class names follow the handoff vocabulary (`.chip`, `.card`, `.sheet`).
- Design tokens exist once, as custom properties in `_tokens.sass`. OCaml
  never duplicates them: `ui/theme.ml` reads the few values it needs (map
  point colours, status-bar colour) with `getComputedStyle` on the root
  element once at startup.
- `webDir` is `_build/default/web/dist` directly, so `npx cap sync` copies exactly
  what dune built and nothing generated is committed. A symlink at the root was
  tried first: Capacitor's copy step reproduces a symlink as a symlink, which
  dangles under `android/`. After `dune clean`, run `dune build @web` before
  `cap sync`. The
  4n illustration and app icons go under `web/img/`.

## 4. `android/` — Capacitor project and Kotlin

Generated once by `npx cap add android` and committed as Capacitor
recommends, with its own generated `.gitignore` for Gradle outputs. Our
edits, all under `android/app/src/main/`:

- `AndroidManifest.xml`: the `VIEW`/`BROWSABLE` intent-filters of
  architecture §7 and the `SEND text/plain` filter for the share target;
  both ship in v1.
- `java/re/bruge/herbier/MainActivity.kt`: generated; only touched if a
  plugin needs manual registration.
- `java/re/bruge/herbier/`: any further Kotlin (a WorkManager constraint
  tweak) as one small Capacitor plugin class inline here, bound from
  `app/bindings/`; no separate plugin package unless a second native piece
  appears.
- `res/`: launcher icons, splash, `strings.xml`.

Keep native code to these files so a later move to a TWA loses nothing.

## 5. `supabase/`

```
supabase/
  config.toml             project settings (sign-ups off, auth providers)
  migrations/             hand-written SQL, `<timestamp>_<verb>_<object>.sql`; the only schema source
  schema/                 generated dump of the current schema, one file per object, committed
    catalog.json          its catalog (lib/postgrest/codegen/catalog.sql), postgrest-codegen's input, committed
  scripts/schema-dump.py  regenerates schema/ (`uv run`); `--check` fails when it is stale
  scripts/smoke.sql       psql asserts on the seeded local db (triggers, plants_near, RLS), run in CI
                          until pgTAP replaces it (M6)
  tests/                  pgTAP: RLS (owner only, no anon), triggers, plants_near
  seed.sql                a dev user and two plants for local `supabase start`
```

No declarative schema and no `db diff`: migrations are written by hand and
`schema/` documents their result. `uv run supabase/scripts/schema-dump.py`
needs the local stack (Docker) with the migrations applied; a schema change
is always two diffs, the migration and the dump, and CI runs `--check`.
`scripts/catalog-dump.sh` (same stack, `--check` in CI too) rewrites
`schema/catalog.json`, from which `app/store/tables.ml` is generated.

The backup/keep-alive cron (`supabase db dump` twice a week) and the dumps
it commits live in the **separate private repo `herbier-backups`**
(`.github/workflows/backup.yml`, `roles.sql`, `schema.sql`, `data.sql`).
Nothing in this repo reads them; this repo only documents the pointer.

## 6. `test/`

```
test/
  domain/       native, alcotest: ids, enum labels, merge rules, link classification, places clustering;
                test_schema_dump: the values of each lookup table in catalog.json are the values of
                the module its `ocaml=` metadata names; the catalog's synced tables
    jsoo/       js_of_ocaml build of domain run under node (needs node >= 19): proves it builds and
                runs under jsoo
  postgrest/    native, alcotest: rendered requests (path, query string, headers, body) and decoded
                responses compared to expected values
    codegen/    native, alcotest: catalog decoding, every metadata rule and error, the emitted AST;
                cli.t (cram) runs the executable
  refs/         native, alcotest: payload decoders and projection over fixtures/
  ui/           native, alcotest: the pure modules of app/ui/ copied in (list_patch, collection_filter)
  store/        native, alcotest: the pure modules of app/store/ copied in (codec, schema, tables, stmt,
                the per-table queries, settings, search, dev_seed); schema SQL, queries, FTS triggers and
                codec run through the sqlite3 CLI (needs sqlite3 with FTS5); not the Capacitor plugin
                (that is #dev/store)
  photos/       native, alcotest: the pure modules of app/photos/ copied in (exif, over recorded
                exifr output in fixtures/exifr_*.json; preview_size; jpeg)
  fixtures/     recorded payloads only: API responses (gbif_<key>.json, wikidata_<key>.json,
                tela_<nn>.json, inpn_<cd_nom>.json) and exifr output (exifr_<name>.json,
                scripts/exifr-fixture.mjs); never app rows
  js/           browser-side tests; added only if the UI spike's leak check fails
```

alcotest runs natively, in `dune test` on every CI job, on every library
without a Brr dependency (`domain`, `postgrest`, `refs`), and on the Brr-free
modules of `store` (`codec`, `schema`, `tables`, `stmt`, `outbox`, the
per-table query modules, `settings`, `search`, `dev_seed`) and of `ui`
(`list_patch`, `collection_filter`). The store ones build statements as
values and never run them, so their SQL runs natively through the sqlite3
CLI (`test/store/sqlite_cli.ml` emulates `Db.edit` without its
transaction). The rest of store (`db.ml`: the transaction, its rollback, the
serialisation), and sync,
photos (except the pure `exif`, `preview_size` and `jpeg`, tested in `test/photos/`), refs_io and geo, are thin over device-only plugins and have no unit
tests; the spikes (architecture §10), dev pages and manual runs cover them.

## 7. `scripts/` and CI

- `scripts/`: `dev.sh` (`dune build @web --watch` + `cap run android -l`),
  `subset-icons.sh` (Material Symbols subset from `icons.txt`),
  `pmtiles-extract.sh` (region extract, v2), `release.sh` (`dune build
  @web`, `cap sync`, `gradle assembleRelease`), `catalog-dump.sh`
  (`supabase/schema/catalog.json` from the local database, §5),
  `emulator.sh` (headless Android emulator: create the AVD, boot, debug
  install, open a dev page; skill `.claude/skills/emulator/`) and
  `webview.mjs` (a dependency-free DevTools Protocol client for the app's
  WebView: eval, page text, screenshot), `exif-fixture-jpegs.py` (`uv run`:
  the Pillow JPEGs behind `test/fixtures/exifr_pil_*.json`) and
  `exifr-fixture.mjs` (exifr output of a photo into
  `test/fixtures/exifr_<name>.json`, with the options of
  `app/bindings/exifr.ml` and `pick` = `Exif.tags`).
- `ci.yml`: `dune build`, `dune test`, the formatting check (`dune build @fmt`,
  ocamlformat installed from opam on the runner), `dune build @web` and checks on
  its output. From M1.9: `dune test` also checks `app/store/tables.ml` against the catalog, and `schema-dump.py --check`,
  `scripts/catalog-dump.sh --check` and `supabase/scripts/smoke.sql` on a local Supabase stack; from M6:
  `supabase test db`.
  `android.yml`: debug APK on tag, manual run, or a pull request touching the
  Android project, uploaded as an artifact for
  sideloading; the only device build until the polish milestone.

## 8. Naming conventions

- `snake_case` files and directories; one module per file; no `types.ml`
  dumping ground, each entity is its own module.
- An `.mli` next to every library module, screens included (they export one
  `make`); `main.ml` and generated `version.ml` have none.
- Generated files (`domain/version.ml`, `supabase/schema/`) start with a
  "generated by" comment and are never edited by hand.
- Bindings are named after the JS package (`cap_sqlite`, `maplibre`), or
  after the DOM API when Brr lacks it (`css_var`), and expose the JS API shape, not our vocabulary. Screens are named after what
  they show, in English, handoff id in the first comment; French strings
  live in the screen, no i18n layer.
- SQL: plural tables, `snake_case` columns, `<timestamp>_<verb>_<object>.sql`.

## Decisions

Taken 2026-09-16.

- One dune library per `app/` subdir (`herbier_<dir>`) plus
  `lib/postgrest/` in its own package; `domain/`, `postgrest` and `refs/`
  also build natively. Dune enforces the dependency direction and the pure
  libraries are tested without a browser.
- Package management: `dune pkg lock`, `dune.lock/` committed; one tool,
  `dune build` alone works in CI. Dune 3.24.2 still labels it experimental;
  an opam switch with a lock file is the fallback if a dependency will not
  lock or build.
- `android/` at root, committed: the tooling assumes it and the manifest
  diff is the whole native layer.
- jsoo output assembled by the `@web` alias into `_build/default/web/dist`;
  Capacitor's `webDir` points at it directly (a root symlink does not survive
  Capacitor's copy step). No copy step, no stale output.
- esbuild bundles `vendor.js` from npm: plugins ship as ES modules and npm
  already exists for the Capacitor CLI.
- Kotlin: one plugin class inline under `android/app/src/main`, until a
  second native piece appears.
- Supabase: hand-written SQL migrations only, no declarative schema, no
  `db diff`. `supabase/schema/` is a per-object dump for documentation,
  regenerated by `scripts/schema-dump.py` and checked in CI.
- ocamlformat `version = 0.29.0`, `profile = default`, `margin = 80`.
- Design tokens: CSS custom properties only, no `tokens.ml` generator;
  `ui/theme.ml` reads the few values OCaml needs with `getComputedStyle`
  once at startup.
- Styles in the indented Sass syntax, not SCSS (dart-sass from npm, compiled by the `@web` alias next to
  esbuild): one file per screen plus shared partials. Mixins and nesting
  keep the styles reusable and concise.
- Tests: alcotest natively on every library without a Brr dependency;
  browser-side tests only if the UI spike's leak check fails.
- `domain/` uses yojson only for the `to_json` / `of_json` of its ids and
  closed value sets (the column codecs). Database rows go through
  `Postgrest` column types; external payload decoding and the projection
  live in `refs/` (domain + yojson, no Brr) so they build natively and run
  against the recorded fixtures; the fetching and orchestration that need
  Brr live in `refs_io/`.
- `lib/postgrest/`: our own generic, sans-IO PostgREST client as its own
  opam package, since no maintained OCaml client exists. Request rendering
  and response decoding are pure and natively tested; the Brr fetch adapter
  is `sync/transport.ml`. The store keeps hand-written SQL and only reuses
  `Postgrest.Row` to decode the plugin's rows: no query DSL over SQLite.
  Column declarations are generated into `store/tables.ml` from
  `supabase/schema/catalog.json` by `postgrest-codegen` (`lib/postgrest/codegen/`),
  shared by store and sync, and checked fresh by `dune test`. sqlgg is a possible later upgrade for the
  store's SQL, pending a spike.
