# OCaml-on-Android stacks for Herbier (beyond Eliom/Cordova)

Date: 2026-09-15. Scope: every plausible way to build the Herbier Android app with as much OCaml as reasonable, *excluding* the Ocsigen/Eliom+Cordova and js_of_ocaml+Cordova/Capacitor routes (covered by another report), but positioning each alternative against that "Cordova shell" baseline. All claims below were checked against sources dated in the text; anything not checked is marked UNVERIFIED.

### Ranked top 3 (solo dev: fun, OCaml purity, finishing)

1. **A. js_of_ocaml / wasm_of_ocaml PWA in a Trusted Web Activity + ~50-line Kotlin shim.** Near-100% OCaml, best dev loop, free static hosting (GitHub/Cloudflare Pages). Versus the Cordova shell you lose guaranteed background execution, silent VIEW-intent capture and native file access; you gain no WebView (Google OAuth is happy: a TWA is Chrome) and a plain web deploy. Spike: day 1, jsoo hello PWA with `share_target`, Bubblewrap build, sideload, confirm it appears in the share sheet and receives a URL; add a Kotlin activity with an unverified `VIEW` filter for `gbif.org` that rewrites to `https://<host>/import?url=...` and launches the TWA, enable it under "Open by default". Day 2, `<input capture>` photo into OPFS, check `navigator.storage.persist()`, one-shot Background Sync upload to Supabase with the app swiped away, MapLibre from jsoo. If intents fail, the same OCaml moves into the Capacitor shell.
2. **C(i). Native OCaml core (opam-cross-android, OCaml 5.4.1, arm64) + Kotlin/Compose UI.** The August 2026 reboot makes real OCaml on the phone credible (lwt, cohttp, tls, yojson cross-built; eio/ctypes/sqlite3 not yet). Spike: install `ocaml-android` on macOS with NDK r29, `dune build -x android` a library, link it with `-output-complete-obj` into `libherbier.so` (UNVERIFIED), load via JNI, run `caml_startup` on a background thread, call Supabase over `tls-lwt-android`, exercise Domains/Threads (Bionic lacks `pthread_cancel`), measure APK size. Pass = the rest is ordinary Compose.
3. **B2. Melange 7 + React Native / Expo SDK 56, hand-written bindings.** Truly native UI, everything via Expo modules, but `rescript-react-native` (0.84.0, 2026-09-15) is ReScript-12-only and Melange dropped ReScript compatibility in 2.0, so you own the bindings. Spike: Expo 56 template, Melange emitting ES modules into Metro with Fast Refresh from `dune build -w`; bind `View/Text/Pressable`, `expo-camera`, `expo-location`, a share-intent module. If four bindings take more than a day, stop.

Not ranked: B1 is the Cordova route with another compiler; D cannot be offline-first; C(ii)/C(iii) have no map or text stack and still need Java; F means reviving lablqml for OCaml 5 and Qt 6 and cross-compiling it before any UI.

## Detailed findings

### Ecosystem baseline (versions checked 2026-09-15)

- OCaml releases (https://ocaml.org/releases): 5.3.0 2025-01-08, 5.4.0 2025-10-09, 5.4.1 2026-02-17, 5.5.0 2026-06-19.
- Upstream cross-compilation: ocaml/ocaml PR #13526 "Simplify the build of cross compilers" merged 2024-12-13 into trunk (https://github.com/ocaml/ocaml/pull/13526); its CI builds cross compilers to MinGW, ARM Linux and Android. OCaml 5.4.0 release notes mention it under "Build system" (`TARGET_BINDIR`; issues #13526, #13789, #13804) (https://ocaml.org/releases/5.4.0). shym's write-up on building a 5.3 cross compiler with those patches, 2025-01-09: https://discuss.ocaml.org/t/building-an-ocaml-cross-compiler-with-ocaml-5-3/15918. Dune cross-compilation still works through ocamlfind toolchains and `-x <toolchain>` (https://dune.readthedocs.io/en/stable/cross-compilation.html).
- js_of_ocaml / wasm_of_ocaml: 6.3 released 2026-02-20 (https://discuss.ocaml.org/t/ann-js-of-ocaml-wasm-of-ocaml-6-3/17834); 6.4 released 2026-06-23 with OCaml 5.5 support, Promise/Fetch/Abort bindings, popover API, pure-Wasm zstd/BLAKE2b, a Stack-Switching effects backend, and (per the announcement) WASI 0.1 support (https://discuss.ocaml.org/t/ann-js-of-ocaml-wasm-of-ocaml-6-4/18282). wasm_of_ocaml runtime requirements: Chrome 119+, Firefox 122+, Safari 18.2+, Node 22+ (WasmGC + tail calls + exception handling); effects: `jspi` default needs Chrome 137+, `cps` runs anywhere, `native` needs Chrome 148+ (https://ocaml.org/p/js_of_ocaml-compiler/latest/README_wasm_of_ocaml.html). Android Chrome is fine for either compiler.
- Melange: 5.0 2025-03-05 (OCaml 5.3, dynamic `import()`) (https://melange.re/blog/posts/announcing-melange-5); 6.0.0-54 2025-11-08 (OCaml 5.3; `Js.Blob/File/FormData`); 7.0.0-55 2026-06-21 (OCaml 5.5); 7.0.1-5x 2026-07-12 (https://github.com/melange-re/melange/blob/main/Changes.md, https://github.com/melange-re/melange/releases). reason-react 0.17.0 2025-12-24 (https://github.com/reasonml/reason-react/releases).
- Dream: opam latest 1.0.0~alpha8, 2024-12-05 (https://opam.ocaml.org/packages/dream/); repo active: Caqti 3.0.0 support 2026-09-04, SIGTERM handling 2026-03-25 (https://github.com/camlworks/dream). dream-html for type-safe HTML/htmx (https://github.com/yawaramin/dream-html). Tarides' 2025 web tooling overview: https://tarides.com/blog/2025-05-15-ocaml-web-development-essential-tools-and-libraries-in-2025/.

### A. js_of_ocaml / wasm_of_ocaml SPA as PWA + Trusted Web Activity (no Cordova)

**Maturity.** Compiler side is the most mature OCaml-to-mobile path there is (see baseline). TWA tooling: Bubblewrap 1.25.0 released 2026-07-31, 1.24.x 2025-09 (https://github.com/GoogleChromeLabs/bubblewrap/releases). PWABuilder is the alternative packager. Android docs for TWA: https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities.

**OCaml share.** ~95%: everything except a service worker (can be jsoo too), the manifest, and, if you go TWA, a generated Android project plus an optional hand-written Kotlin activity.

**Capabilities.**
- Camera: `getUserMedia` and `<input type=file accept=image/* capture=environment>` both work in installed PWAs on Android Chrome; `ImageCapture.takePhoto` gives full-resolution blobs (https://developer.chrome.com/blog/imagecapture, https://simicart.com/blog/pwa-camera-access/ 2025). Rated easy.
- Geolocation: standard. In a TWA you may additionally enable "location delegation" so the permission is the app's, not Chrome's; there was a 2022 bug where delegation swallowed the prompt (closed) (https://github.com/GoogleChrome/android-browser-helper/issues/363). Rated easy.
- Map: MapLibre GL JS on WebGL; nothing Android-specific. Easy.
- Storage: IndexedDB + OPFS. OPFS shipped on Android Chrome (all of File System Access minus `show*Picker()` and drag-drop) (https://groups.google.com/a/chromium.org/g/blink-dev/c/GyxqF8ZDK5Q, https://issues.chromium.org/issues/40235519). `navigator.storage.persist()` is granted silently by Chrome based on engagement/installation/notification permission; installed PWAs qualify (https://web.dev/articles/persistent-storage, last updated 2020-05-12; MDN quotas/eviction https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria). Quota is large (GBs, device-dependent) but exact figure is not documented for Android. Rated doable: store previews in OPFS, originals go to Google Photos/Drive.
- Background upload: one-shot Background Sync is supported on Chrome Android (caniuse: Chrome Android 152 supported, Firefox Android and Safari not) (https://caniuse.com/background-sync). Periodic Background Sync is Chrome-only, installed-PWA-only and throttled by site engagement (https://developer.mozilla.org/en-US/docs/Web/API/Web_Periodic_Background_Synchronization_API, https://developer.chrome.com/docs/capabilities/periodic-background-sync updated 2025-08). Background Fetch is "limited availability / experimental", Chromium-only (https://developer.mozilla.org/en-US/docs/Web/API/Background_Fetch_API). Practical pattern: queue uploads in IndexedDB, register a `sync` tag, and also flush on app open. Rated painful because nothing guarantees the upload completes while the app is closed, unlike a Cordova/Capacitor background plugin or a Kotlin WorkManager job.
- Google sign-in for Drive/Photos: Google Identity Services popup/redirect works in Chrome; Google's ban is on embedded WebViews (`disallowed_useragent`), and Custom Tabs / the system browser are explicitly allowed (https://developers.googleblog.com/upcoming-security-changes-to-googles-oauth-20-authorization-endpoint-in-embedded-webviews/, 2021-06-29). A TWA *is* Chrome, so this works; use Supabase Auth's Google provider with PKCE redirect to keep it simple. Rated easy. Note: this is one place where a plain WebView shell (Cordova/Capacitor) is *worse* than a TWA.
- SEND share target: Web Share Target works for PWAs installed via Chrome (https://developer.chrome.com/docs/capabilities/web-apis/web-share-target). Bubblewrap supports `shareTarget` in `twa-manifest.json` and Chrome documents the required `ACTION_SEND` intent-filters (https://developer.chrome.com/docs/android/trusted-web-activity/web-share-target, last updated 2020-11-10). Bug reports: bubblewrap #698 (opened 2022-05-19, still open) and PWABuilder #4905 (opened 2025-04-26, closed without documented fix) say share target sometimes fails in packaged APKs while working from "Add to Home Screen" (https://github.com/GoogleChromeLabs/bubblewrap/issues/698, https://github.com/pwa-builder/PWABuilder/issues/4905). A 2025 write-up says an absolute `action` URL fixes most cases (https://martin.hjartmyr.se/articles/pwa-web-share-target-android/). Rated doable; verify on day 1 of the spike.
- VIEW/BROWSABLE capture of gbif.org links: the manifest `handle_links` only captures links *inside the PWA's own scope* (https://developer.chrome.com/docs/capabilities/pwa-url-handler; state as of 2026-07-24: works on Android when installed through Chrome, https://modernwebweekly.substack.com/p/the-state-of-link-capturing-in-pwas). `scope_extensions` would need gbif.org to host `/.well-known/web-app-origin-association` and is "not supported on mobile platforms" anyway (https://developer.chrome.com/docs/capabilities/scope-extensions). Android App Links require gbif.org to publish `assetlinks.json` for your app, which will never happen. What remains: an ordinary, *unverified* `VIEW` intent-filter for `gbif.org` in your own Kotlin activity; since Android 12 the user must enable it under "Open by default > Add link", after which your app is offered. The activity then rewrites the URL to `https://<yourhost>/import?url=...` and launches the TWA (navigating the TWA to a non-validated origin would show Custom-Tab chrome, https://developer.chrome.com/docs/android/trusted-web-activity/multi-origin). Rated painful and requires the Kotlin shim; the Cordova shell does this with a plugin.
- UI (rich species page, fonts, bottom sheets, swipes): plain web; easy.

**Hosting.** GitHub Pages: 1 GB site, 100 GB/month soft bandwidth, 10 builds/hour (https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits). Cloudflare Pages free tier equivalent. The TWA needs `/.well-known/assetlinks.json` on that host.

**Dev loop.** `dune build -w` + browser reload, desktop DevTools, then `bubblewrap build` for the device; no Gradle in the inner loop.

**Bundle.** wasm_of_ocaml or jsoo output of a few hundred KB to a couple of MB; TWA APK ~1-2 MB.

**What is lost vs a Cordova shell.** Reliable background upload, VIEW intent capture without user configuration, direct file-system/MediaStore access, arbitrary native plugins. What is gained: no WebView, Chrome's OAuth policy compliance, trivially updatable app (it is just a web deploy).

**Top risk.** Share/VIEW intents in the packaged TWA and the background-upload guarantee. Both are testable in the first day.

### B. Melange

**B1. Melange + reason-react inside a WebView shell (Cordova/Capacitor).** Same capability profile as the jsoo+Cordova route documented elsewhere; the difference is the compiler: Melange 7 emits readable ES modules that Vite/Metro bundlers consume natively, supports OCaml 5.5, and has a JS-idiomatic FFI (`[@mel.*]`) that makes binding Capacitor plugins quick. OCaml share ~90%. Position: pick it over jsoo only if you want React and npm-style interop; pick jsoo/wasm_of_ocaml if you want OCaml-native libraries (Lwt, Brr, Eio-less code) and no npm at all.

**B2. Melange + React Native / Expo.** Status 2026:
- `rescript-react-native` is alive (0.84.0 committed 2026-09-15, RN 0.85/0.84 era, ReScript 12 with `.res.js` output) but it is ReScript-only (https://github.com/rescript-react-native/rescript-react-native). Melange removed its ReScript compatibility layer in 2.0 (2023) and the two ecosystems have diverged (https://dev.to/redbar0n/rescript-vs-melange-2h90), so those bindings cannot be consumed from Melange.
- No `melange-react-native` package exists in the melange-re org (https://github.com/orgs/melange-re/repositories); the only public template is `kxcdev/kxc-melange-react-native-template`, last commit 2024-07-09 (https://github.com/kxcdev/kxc-melange-react-native-template). Verdict: "alive as DIY, dead as a maintained ecosystem".
- Expo: SDK 55 (RN 0.83, React 19.2) and SDK 56 (released 2026-05-21, RN 0.85) are New-Architecture-only (https://expo.dev/changelog/sdk-56-beta, https://docs.expo.dev/guides/new-architecture/). Every capability exists as an Expo module (expo-camera, expo-location, expo-sqlite, expo-background-task, expo-auth-session, expo-linking + a share-intent library, `@maplibre/maplibre-react-native`, `@gorhom/bottom-sheet`), each needing a hand-written `external`.

OCaml share ~70% (bindings count). Dev loop: Metro Fast Refresh works on Melange output if `dune build -w` emits into the Metro root. APK 25-45 MB. Top risk: binding maintenance across RN upgrades; for a solo hobby app this is the stack most likely to stall.

### C. Native OCaml on Android

**Toolchain (the big 2026 change).** `ocaml-cross/opam-cross-android` was fully rebooted by Romain Beauxis (toots, Liquidsoap maintainer), announced 2026-08-09 (https://discuss.ocaml.org/t/ann-ocaml-android-reboot/18432; OCaml Weekly News 2026-08-11 https://alan.petitepomme.net/cwn/2026.08.11.html). README (https://github.com/ocaml-cross/opam-cross-android): OCaml 5.4.1, target `aarch64-linux-android` only, NDK r29 (older untested), hosts macOS and x86_64 Linux, API level default 26, install via `opam repository add android ... && opam install ocaml-android`, build with `dune build -x android`. Runtime patch: Bionic has no `pthread_cancel`, so OCaml's shutdown call to it is patched out (extra domains left running at exit are not killed). Commits through 2026-08-15 add cohttp-lwt-unix, conduit, tls, ca-certs, memtrace, and a CI matrix building every affected package. Package list on 2026-09-15 (~80): lwt, cohttp(+lwt, +unix), conduit, tls(+lwt), x509, mirage-crypto*, yojson, zarith (via build-gmp), cmdliner, logs, fmt, ptime, uri, re, angstrom, ppxlib, ppx_sexp_conv, digestif, base/stdio/fieldslib, memtrace, and more. **Missing so far:** eio, ctypes, sqlite3, domainslib, zlib/camlzip, decompress; the old package set lives on the `old-main` branch. The 5 open issues are all pre-2020 leftovers. Vouillon's `ocaml-android` / `opam-android-repository` are 2014-era and irrelevant now (https://github.com/vouillon/ocaml-android). Kakadu replied on the announcement suggesting a raylib-ocaml demo; none exists yet.

**Runtime concerns.** OCaml 5 domains/threads: Bionic pthreads are fine apart from the `pthread_cancel` patch; Unix library builds (cohttp-lwt-unix is packaged). JNI: no maintained OCaml/JNI bridge for Android (camljava is desktop JVM: https://github.com/xavierleroy/camljava); the recognised recipe is `ocamlfind -toolchain android ocamlopt -output-complete-obj` (or `-output-obj`) into a `.so`, then a handful of C stubs exported to JNI that call `caml_startup` once on a dedicated thread and marshal via `caml_callback`. Old reports of `caml_startup` segfaults with the 4.x toolchain (https://discuss.ocaml.org/t/has-anyone-used-opam-cross-android-with-the-jni-to-actually-build-an-apk/1241) are not evidence about the 2026 toolchain: UNVERIFIED either way; it is the first thing to spike.

**C(i) OCaml core as a shared library + Kotlin/Jetpack Compose UI.** Camera (CameraX), GPS (FusedLocation), MapLibre Android SDK, MediaStore gallery, Room/SQLite, WorkManager uploads, Credential Manager Google sign-in, intent-filters for SEND/VIEW, Compose bottom sheets: all "easy", all Kotlin. OCaml owns the domain model, sync engine, Supabase client (cohttp+tls are cross-built), GBIF parsing, offline queue, maybe Markdown-to-HTML for species pages. OCaml share 30-50% by lines, but arguably the interesting half. Dev loop: NDK cross-build (seconds with dune) + Gradle (slow) + JNI marshalling boilerplate. APK 5-15 MB. Top risk: the JNI/`caml_startup` embedding and the missing `ctypes`/`sqlite3` cross packages (you can port them; the reboot's `build-<lib>`/`conf-<lib>-android` pattern is designed for it).

**C(ii) SDL2/raylib OCaml GUI.** raylib-ocaml 2.2.1 (released 2026-07-12; raylib 6.0.0 built from source via ctypes) has no Android mention or example (https://github.com/tjammer/raylib-ocaml); raylib itself supports Android via `android_native_app_glue`, so you would compile the OCaml program with `-output-complete-obj` into `libmain.so` under a NativeActivity: nobody has published this. Bogue 20260208 (2026-02-10) is SDL2-only ("does not work with SDL3 yet"), touch-aware, desktop-oriented (https://github.com/sanette/bogue, https://ocaml.org/p/bogue/latest); tsdl 1.2.0 needs SDL 2.0.22+. Either way you would still write Java for camera, GPS, share intents, sign-in, and you would have to build a slippy map renderer and a rich-text layout engine yourself. Not realistic for Herbier; fine for a game.

**C(iii) Skia / NanoVG bindings.** `oski` (Skia binding, https://github.com/syaiful6/oski), `graphv` (NanoVG port, native + web, https://ocaml.org/p/graphv/latest), `wall` (let-def, https://github.com/let-def/wall): rendering primitives only, no widgets, no Android build recipes, no text layout beyond basics. Blocked for this app.

### D. OCaml on the server only: Dream + htmx served to a PWA/TWA

**Maturity.** Dream alpha8 (2024-12-05) with steady 2026 commits; dream-html + pure-html for typed markup with htmx attributes; form validation and htmx patterns documented in 2025 (https://dev.to/yawaramin/powerful-form-validation-with-ocamls-dream-framework-4ggj). OCaml share ~80% (htmx attributes and a little JS for camera/GPS/map). Capabilities: camera/GPS/map/gallery are browser-side and easy; sign-in is a plain server OAuth flow (easy); share target and link capture are the same as stack A (the share_target `action` just posts to Dream). **Offline-first is the deal-breaker:** htmx needs the server for every interaction; caching rendered pages in a service worker gives read-only offline, but recording a plant in the field with no signal needs a client-side queue and local rendering, i.e. exactly the jsoo client you were trying to avoid. Background upload also ends up client-side (stack A's limits).

**Hosting (checked 2026-09).** Fly.io: no free tier for new accounts since Oct 2024, trial only; smallest machine shared-cpu-1x/256 MB about $2.02/month, volumes $0.15/GB, snapshots billed since 2026-01-01 (https://fly.io/docs/about/pricing/, https://www.saaspricepulse.com/tools/flyio). Railway: one-time $5 trial credit, then Hobby $5/month (https://docs.railway.com/pricing/plans, https://bex.co/blog/2026/07/29/railway-free-tier-trial-credit). Oracle Cloud Always Free ARM: quietly cut from 4 OCPU/24 GB to 2 OCPU/12 GB effective 2026-06-15, enforced 2026-08-18, and "out of host capacity" remains common (https://www.infoq.com/news/2026/07/oracle-cloud-free-tier-limits/). Hetzner: CX22 about EUR 4.35/month, ARM CAX11 about $3.79, with a price adjustment announced for 2026-04-01 (https://www.hetzner.com/cloud/regular-performance/, https://betterstack.com/community/guides/web-servers/hetzner-cloud-review/). Supabase already hosts the data, so this server would exist only to render HTML: poor value for a single-user app.

### E. Everything else

- **wasm_of_ocaml + WASI in a JVM Wasm runtime (Chicory) inside a Kotlin app.** The WASI backend (PR #1831) was described on 2026-06-09 as a working prototype on a branch running on Wizard, Wasmtime and Node with `--effects=cps` (https://ocaml.org/backstage/2026-06-09-wasm-of-ocaml-on-wasi-a-working-prototype-looking-for-a-production-user); the 6.4 announcement two weeks later lists "WASI 0.1 support". Chicory 1.0.0 (2024-12) is a pure-JVM runtime with WASI preview1, Android API 28+ (https://github.com/dylibso/chicory, https://chicory.dev/blog/chicory-1.0.0/), but wasm_of_ocaml output requires WasmGC, tail calls and exception handling; Chicory's WasmGC support is UNVERIFIED and most likely absent, so treat as blocked. Native wasmtime on Android via JNI would work but then you might as well ship native OCaml (stack C).
- **Flutter with an OCaml core via dart:ffi.** Mechanically identical to C(i) with Dart instead of Kotlin (load `libherbier.so` with `DynamicLibrary.open`, https://docs.flutter.dev/platform-integration/android/c-interop); no OCaml examples found. Only worth it if you prefer Flutter's UI to Compose.
- **Kotlin Multiplatform with OCaml.** Same as C(i) (cinterop/JNI against a static or shared OCaml library); nothing OCaml-specific exists.
- **OCaml to Lua/Godot, Hazel:** nothing usable found; skipped.

### F. Qt for Android driven from OCaml (lablqml)

**Bindings.** lablqml (Kakadu): latest opam release 0.7 on 2021-07-02, constraint `ocaml >= 4.10 & < 5.0`, Qt 5.3+ only (https://opam.ocaml.org/packages/lablqml/, https://github.com/Kakadu/lablqml). Master's last commit is 2024-01-27; an `ocaml5` branch has exactly one commit, "WIP on ocaml 5 demos", dated 2026-08-08; an `android` branch ("Android crosscompilation support") dates from 2017-01-12 (Qt 5, OCaml 4.04 era). No Qt 6 support anywhere. Other bindings: `let-def/cuite` (Qt widgets) is archived (https://github.com/let-def/cuite); `mrvn/ocaml-qt5` last touched 2023; `mlsmoke` 2019. Conclusion: no OCaml 5 / Qt 6 binding exists; F starts with porting lablqml's PPX + C++ glue.

**Qt side (if the binding existed).** Qt 6.11 docs: Qt Location is a supported module (not Technology Preview) with OSM and items-overlay plugins, LGPLv3/GPL (https://doc.qt.io/qt-6/qtlocation-index.html); MapLibre Native Qt plugin v3.0.0 (2024-10-11) supports Qt 6.5+ on Android, v4 in development (https://github.com/maplibre/maplibre-native-qt/releases). Camera via QtMultimedia `Camera` inside `CaptureSession` works on Android with the usual forum-reported quirks (https://doc.qt.io/qt-6/qml-qtmultimedia-camera.html, https://forum.qt.io/topic/149927/qml-camera-does-not-work-on-android). GPS via the QtPositioning `android` plugin (https://doc.qt.io/qt-6/qtpositioning-android.html). Intents (SEND/VIEW reception) require subclassing `QtActivity` in Java, overriding `onNewIntent`, and reaching OCaml through `QJniObject` (https://ekkesapps.wordpress.com/qt-6-qmake/qjniproject-android-extras/, https://somcosoftware.com/en/blog/how-to-interface-qt-with-android-java-code-2023). Background upload: Qt Android Services (Java `Service`/`QtService`, one Qt service per process) (https://doc.qt.io/qt-6/android-services.html). Storage: QtSql SQLite, easy. OAuth: Qt Network Authorization is GPLv3-only in Qt 6 (https://doc.qt.io/qt-6/licensing.html), so either accept GPL for the app or open Custom Tabs via `QDesktopServices` and catch the redirect through a VIEW intent. Licensing: Qt for Android links dynamically by design and The Qt Company says this is "recommended and supported", so LGPLv3 obligations are satisfied by shipping the Qt `.so`s (https://wiki.qt.io/Licensing-talk-about-mobile-platforms).

**Combining with cross-compilation.** Qt's Android build produces `libapp_arm64-v8a.so` loaded by `QtActivity`; the OCaml runtime would have to be linked into that library (`-output-complete-obj` from the ocaml-android toolchain) together with lablqml's C++ stubs compiled by the same NDK clang and Qt's CMake. Every layer is individually plausible and nobody has done the stack with Qt 6 + OCaml 5. OCaml share ~50% (QML + JS for UI, OCaml for models exposed as QObjects). Dev loop: Qt Creator deploy cycles, QML hot reload only for pure QML. APK 30-60 MB. Rated: every capability "doable" on paper, but the entry cost (revive lablqml for OCaml 5 and Qt 6, cross-compile it, embed the runtime) is weeks before the first screen. Ranked below C(i), which reaches the same capabilities with Compose and no binding archaeology.

### Positioning against the Eliom/Cordova baseline

- A is the "same OCaml, less shell": choose it if the intent and background tests pass on day 1; keep Cordova/Capacitor as the fallback container for the same jsoo code.
- B1 is the Cordova route with Melange's FFI and React; not a separate decision.
- C(i) is the only stack where OCaml runs natively on the phone with a modern toolchain (2026-08 reboot); it trades OCaml share for native reach.
- B2, D, E and F are either DIY-binding-bound, offline-incompatible, unverified, or unmaintained.
