# Herbier — Implementation plan

Status: decided, 2026-09-16 (see Decisions at the end). Orders the work
needed to reach the mockup (`design_handoff_herbier/README.md`, screens
4a–4n and 5a–5f, and tour 6's identification screens 6a–6k, added
2026-11-16 as M9) with the modules of `layout.md`, the decisions of
`stack.md` and the design of `architecture.md`. The spikes of
architecture §10 are absorbed as the first steps of the milestone that
needs them: spike 1 (shell) → M0.4, M4.39, M7.52; spike 2 (storage) →
M1.10, M1.12, M3.27; spike 3 (map) → M5.40 (its offline half is v2);
spike 4 (auth) → M6.46, M7.51; spike 5 (references) → M4.35; spike 6 (UI)
→ M2; spike 7 (identification) → M9.63.

Conventions: one step = what gets written · what it depends on · done when.
Screen ids refer to the handoff; a screen is "functional" when it renders
from the local store and every action on it that does not need a later
milestone works. Each milestone ends in something runnable in a browser
(`dune build @web` + a static server) or on the phone (`scripts/dev.sh`).

The current row is built in SQL with `json_object` over the local columns (timestamps as stored, which the row specs decode). `architecture.md` §4 now says a migration adding a column to a synced table rewrites the queued payloads. The push order was already parents first (`seq`, `test_push_order`); on the phone every parked photo's observation entry had a lower `seq`. The photos' 409 body is recorded from the local stack (`sync_upsert_photos_fk_409.json`). After installing this build the user's 46 entries are retried on the first cycle, with no tap.

## Decisions

Taken 2026-09-16; the toolchain ones are in `layout.md`.

- The local store comes first (M1) and the UI spike (M2) runs on real rows; `test/fixtures/` keeps recorded API payloads only. No throwaway data layer, and the spike exercises the queries it will live on. Addendum 2026-11-10 (M3.26): "recorded API payloads" widens to recorded external payloads (API responses, library output such as exifr's), still never app rows.
- Photos (M3) before sync (M6): photos are the field workflow, text rows can wait.
- Offline map region is v2; v1 uses online tiles only.
- Link interception in v1 = the SEND share target and the VIEW intent-filters, Pl@ntUse host included. Narrowed 2026-11-12: intercepted hosts are Pl@ntNet's only (`identify.plantnet.org`, Pl@ntUse); other reference hosts are recognised only when pasted (gbif.org may be re-added if needed).
- Tests: alcotest natively on `domain/`, `lib/postgrest/`, `refs/`; browser-side tests only if M2.20 fails its leak check.
- Package management: `dune pkg lock` from M0; opam switch with a lock file as the fallback.
- References are fetched eagerly at link time, in the background: 4j promises it and 4f then works offline.
- Device builds are debug-signed sideloads from `android.yml` artifacts until M8. From M8.56 they are signed by the user's release key (`scripts/release.sh`, also with `--debug`), and `android.yml` builds the signed release on a `v*` tag.
- ~~Regional (France-only) sources are skipped until the region is decided.~~ Decided 2026-11-12: France-focused, works elsewhere; INPN and Tela Botanica are an optional regional layer (M4.59) whose rows show only when they have data.
- Camera: in-app viewfinder via the browser camera stream; `camera-preview` plugin as the fallback (R4).
- The Google Photos row is removed from 4m; the storage radio offers Drive and app-only.
- Identification is in scope (user decision 2026-11-16, Claude Design tour 6): Pl@ntNet's identify API names a plant from its photos (M9). It adds to link interception, which is unchanged (Pl@ntNet's hosts only); architecture §11's non-goal narrows to identification on the device.
- With M9 (2026-11-16, from the design and M5.57's privacy rule): an identification sends previews only (canvas re-encodes: no EXIF, so no position) and the flora's id, never a position (the flora list is asked without `lat`/`lon`) nor an original; nothing about it is stored (choosing writes the rows a search pick or a link writes); no request leaves without a tap, except Enregistrer in Noter with « Identifier dès la photo » on (M8.76; it was the first photo of a Noter session until M8.75): no automatic retry, no identification of the « À identifier » queue in the background.
- **Clé API Pl@ntNet — decided by Tristan on 2026-11-16: option C**, in his words: « une clé dans les réglages c'est bien pour le moment. 500 c'est largement suffisant pour une app que seul moi utilise. et si on maintient une clé chacun, pas de problème ». The key is the user's own, typed in 4m (« Clé API Pl@ntNet », a row the design does not have, M9.66), one key per user, each with its 500 identifications a day. It is not built into the APK and there is no Supabase Edge Function. It is stored only on the device (Capacitor Preferences, `plantnet.api_key`), never synced to Supabase, left out of Android's backups like the session, and never logged; identification works signed out and while the project is paused. With no key, the Identifier buttons (6i, 6k) are disabled with one line pointing to Réglages (4h's, M8.76, is disabled with no line, by the user's decision; 6a left Noter with M8.75), as the « Google Drive » radio is in a build without a web client id, and « Identifier dès la photo » does nothing. Per Pl@ntNet's documentation the key must still be exposed with `https://localhost` as an authorized domain, since the WebView's calls are browser calls; the key row's help text says so and M9.63 checks it (R10). Options A (built in, exposed) and B (Edge Function) are kept in `exploratory_research/plantnet-identify-api.md` §10.
- **Flore par défaut — decided by Tristan on 2026-11-16: `all` (« Automatique »)**, in his words: « using 'europe de l'ouest' would make it harder to identify non-indigenous plants ». The design shows a fixed flora, « Europe de l'Ouest » (a placeholder: that is the name of the legacy `weurope` flora, whose model Pl@ntNet will drop); « Automatique » replaces it as the default. Pl@ntNet picks the most relevant flora per request and names it in its answer, which keeps « France-focused, works elsewhere » and sends no position; the flora list stays selectable in 4m and 6c, so a regional flora (`k-southwestern-europe` for France) is one tap away, since Pl@ntNet says a pinned flora gives better results.
