# Comment hygiene review

Comments introduced or touched by the change. The rule (`style-guide.md` §13): doc comments in
`.mli` files say what a value is for; `(* *)` in `.ml` files only say *why*, and only when the
code cannot. Rationale, alternatives, process and plans belong in the commit message, the PR
body or `docs/`.

## Scope

- Comments on lines the diff added or modified, in any language: `(* *)` in OCaml, `--` in
  SQL, `//`/`/* */` in JS, Kotlin and Sass, `#` in Python, shell, TOML and YAML, `;` in dune
  files. A pre-existing comment is in scope only when the change made it wrong; say so.
- Doc comments (`(** *)`) are comments with another syntax: every rule applies, with the one
  allowance below.
- `docs/**` edits are in scope for §5 only.
- Never flag generated or recorded files (`*.opam`, `dune.lock/**`, `supabase/schema/**`,
  `test/postgrest/fixtures/scenarios.json`, `app/domain/version.ml`).

## What to flag

### 1. Comments about things that are not in the code

- Future or speculative features: "when we support X", "for now only A".
- The plan or the process: "step 3", "M1.11", "first pass", "per the plan". A step id in a
  commit message is right; in the code it is noise.
- A conversation or an agent: "as discussed", "the reviewer asked", "Claude", a session link.
- Vocabulary that exists only in a doc or a review thread and nowhere in the file's
  identifiers. If the concept matters, it is a name in the code.

Allowed: a one-line pointer to a doc section or an upstream issue (`(* see architecture.md §4 *)`,
`(* workaround for ocaml/dune#1234 *)`). A pointer wrapped in three lines of retelling is a
finding; keep the pointer.

### 2. Comments that restate the code

`(* increment i *)`; a doc comment that repeats the signature; a section banner above a single
obvious function; a type annotation claim already made by the type.

### 3. Prose that belongs elsewhere

Design decisions, rejected alternatives, history ("we used to") → commit message, PR body or
`docs/`. A comment longer than the code it describes. A comment standing in for a bad name →
propose the rename, delete the comment.

### 4. Comments that do not help

Stale or contradicted comments; commented-out code; debug leftovers; `TODO`/`FIXME` with no
owner and no step or issue reference; decorative banners; a licence header the repo does not
use.

### 5. Docs

A `docs/notes/` or `docs/exploratory_research/` file added for something that is a commit
message; a decision recorded in a note instead of `stack.md` or `architecture.md` where the
project keeps decisions; a plan step rewritten in a doc other than `plan.md`.

## What NOT to flag

- `.mli` doc comments that carry what the signature cannot: units, invariants, error cases,
  the shape of a JSON payload, "never call inside an update step".
- The AI policy file and the "generated by" first line of generated files.
- SQL migration comments recording a decision the DDL cannot show (why a constraint is absent,
  why a policy is looser than it looks): keep them however long. Never flag `COMMENT ON`.
- `(* style: ... because ... *)` deviations the style guide allows, when they give the reason.
- Directives: `[@@@warning ...]`, `[@ocaml.doc ...]`, `(* ppx *)` markers, shebangs.
- Section separators in test files grouping tests by concern.

## Judgment

For each candidate: could a reader get this from the code? If yes, delete. Is it a property of
the code or of something outside it? If outside, delete and name where it belongs. Prefer
delete over shorten, rename over keep, a one-line pointer over a retelling. Judge against these
rules, not against neighbouring files.

Severity caps at `medium` (stale or misleading, or about a plan, a conversation, an agent);
`low`/`nit` for taste. Comment hygiene never blocks a PR.

## Output

Write `.review-report/comment-hygiene.md`:

```
# Comment hygiene review

## Findings
| Severity | Location | Issue | Suggestion |
| --- | --- | --- | --- |
| medium/low/nit | path:line | quote the comment and the rule it breaks | delete / replace with X / rename Y |

## Accuracy pass (claims checked, no findings)
- <comment> at <file:line> claims <X>; verified against <file:line> — holds.

## Questions for the author
- ...
```

The accuracy pass section is required even when empty: checking a comment's claim against the
code it describes is the most valuable and most expensive part, and a reviewer who did it and
one who skipped it must not file the same report. Review only; no edits.
